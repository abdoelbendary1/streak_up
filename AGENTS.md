# StreakUp operational rules

- Codex owns planning and implementation. Read the task-specific code/tests and relevant controlling sections only. Preserve existing working-tree changes; use the requested branch and repository. Never commit/push without authorization.
- Product behavior comes from docs/PRD.md and approved feature specifications. Technical boundaries come from the Constitution, ARCHITECTURE.md and DATABASE.md. The Product Owner approved the Lean Feature Workflow on 2026-10-01; legacy pipeline instructions in historical artifacts or optional local skills do not reinstate retired stages.
- Default workflow: Understand + Specify → Design Reference (if UI exists) → Plan → Implement + Test → Finalize. Spec Kit remains lightweight: concise spec.md and plan.md; tasks may be inside the plan. Clarification, tasks.md, separate consistency analysis and review are optional. Ask only for a genuine blocking product decision. Check consistency while planning. CodeRabbit is removed from future delivery.
- UI requires an approved design/PNG before implementation; cite exact references. Codex does not explore designs. Implement functional UI reasonably close to the reference; final visual polish belongs to a later Product Owner pass. Check required states, interactions, overflow, structural RTL, compact constraints, keyboard/insets and accessibility proportionately. No exhaustive screenshot matrix or pixel-perfect gate.
- Organize aggressively, abstract conservatively. Feature-first outside; actual responsibilities inside: presentation/cubit, screens, widgets, sheets, dialogs; application, domain/models/repositories and data/datasources/repositories/storage only where useful. No empty layers or pass-through use cases, generic services, base repositories, SDK drivers or duplicate gateways.
- Global systems own only genuinely global state. AuthSession owns serialized account/session transitions and cleanup; AuthCubit owns loading/errors. GoRouter owns location; ShellCubit owns shell presentation only. Global feedback owns temporary notifications; feature errors stay local. Connectivity excludes syncing/syncFailed. Do not model future infrastructure in presentation before it exists.
- Preserve account isolation, stale-event rejection, recovery isolation, cleanup-before-rebind, privacy/redacted logging, database/RLS and local-first contracts. This foundation task does not authorize SL-03, remote migrations or product schemas.
- Screen → meaningful sections → small widgets; pass values/callbacks, use conventional Flutter, tokens and constraints, one scrolling owner, local temporary visual state. Avoid deep Cubit lookups, giant screens, one-widget-per-file rules and speculative UI frameworks. Keep comments explaining why; requirement IDs belong primarily in specs/tests.
- Feature screens compose and dispatch raw intent; Cubits normalize/validate and own command feedback/completion. Typed input errors stay separate from application failures. Keep visual editing state local, observable dependencies explicit and application snapshots read-only; no fake rebuilds.
- Use meaningful forms/sections and semantic shared recipes; standard Flutter first, custom mechanisms only for measured constraints. Destinations own scrolling/insets. Keep main.dart as the entry point and bootstrap orchestration focused. Preserve explicit generation/account guards and the data source's persistence barrier. Human maintainability is an acceptance check; see Feature Code Rules in the guidelines.
- Constructor injection; generated Injectable DI (`get_it` + `injectable`) resolves dependencies without changing architectural ownership; generated typed go_router routes and localization. Use the right external tool at the data boundary: Supabase Flutter for Auth; Dio for Supabase REST feature data. Presentation never depends on transport. Never edit generated output. Run normal generators when source changes require them. Remove dependencies/strings only when proven unused.
- Finalize code changes with flutter analyze --no-pub, relevant tests (full suite for shared/auth changes), git diff --check, IMPLEMENTATION_GUIDE.md and feature/project-state updates. Runtime checks are lightweight and used where useful; do not imply live/platform evidence passed. Documentation-only edits need consistency/link checks.

See [engineering guidelines](docs/engineering/PRAGMATIC_FLUTTER_GUIDELINES.md) and [stage playbook](docs/engineering/CODEX_STAGE_PLAYBOOK.md).
