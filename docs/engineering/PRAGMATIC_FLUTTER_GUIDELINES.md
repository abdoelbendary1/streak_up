# Pragmatic Flutter engineering

Approved foundation amendment: 2026-10-01. The [historical audit](../refactoring/SL01_SL02_SIMPLIFICATION_AUDIT.md) retains its original findings; the implementation guides describe current code. Follow the [Lean Feature Workflow](CODEX_STAGE_PLAYBOOK.md), approved product/design behavior and database/privacy contracts.

1. **Organize aggressively, abstract conservatively.** Feature-first outside; actual responsibilities inside. Use presentation/cubit, screens, widgets, sheets and dialogs where they exist. Add application, domain/models/repositories and data/datasources/repositories/storage only for genuine responsibilities. More useful files are welcome; empty layers, symmetry-only layers and unnecessary classes are not.
2. **Start with data flow.** Identify inputs, outputs, owner, transformations, dependencies and business rules before choosing classes. Do not model future infrastructure inside presentation before it exists.
3. **Justify boundaries.** SDK isolation, account lifecycle, meaningful tests, shared rules and real business responsibilities justify abstractions. Do not add one use case per operation, gateway/repository/data source duplication, a driver beneath a data source, base repositories, generic services or pass-through wrappers.
4. **Global systems own only genuinely global state.** AuthSession owns authoritative lifecycle, serialized transitions, stale-event rejection, recovery context and account cleanup. AuthCubit owns presentation loading/errors. GoRouter owns navigation/location. ShellCubit owns only shell presentation. Global feedback owns temporary success/information/warning/recoverable-error notifications. Feature inline errors/retry stay with that feature; no action-key registries or background-sync aggregation.
5. **Separate connectivity and sync.** Reachability may be online, offline or reconnecting/checking when needed. It cannot prove backend access from an interface signal alone. Syncing/syncFailed are not network states. Shell owns no application's action sync map. Pending/Synced/Failed badges accept values from their owning feature or future SL-03; local completion never implies remote acknowledgment.
6. **Keep safety explicit.** Preserve verified-session admission, recovery isolation, cleanup-before-rebind, account ownership, redacted logging, stale-result rejection and recoverable intent. Offline transport is not confirmed auth expiry. Route guards are UX, not server authorization.
7. **Conventional Flutter UI.** Screen → meaningful sections → small local/reusable widgets. Pass values/callbacks rather than deep Cubit lookups. Keep temporary editing/focus/visibility local; business state belongs to feature/application owners. One clear scrolling owner; standard layout primitives, constraints and theme/tokens first. Avoid giant screens, arbitrary magic values, generic form/UI engines and a one-widget-per-file rule. Keep shared primitives only for real reuse.
8. **Implement approved designs proportionately.** UI requires approved PNG/design before implementation; Codex does not explore designs. Functional and reasonably close is the implementation target. Verify required states, interactions, obvious overflow, RTL, keyboard/insets, compact phones and accessibility. No exhaustive screenshot matrix or pixel-perfect gate; final polish belongs to the Product Owner. Preserve unverified release/platform checks accurately.
9. **Use established tools.** Constructor injection, generated Injectable DI (`get_it` + `injectable`), generated typed go_router and ARB localization. Use the right external tool at the data boundary: Supabase Flutter for Auth; Dio for Supabase REST feature data. Presentation never depends on transport. Generated Injectable resolves dependencies; it does not change architectural ownership. Observable API logging records development traffic cleanly with strict data redaction. Minimal transport failure classification maps Dio errors into typed categories. SDK operations live in data sources, result mapping in repository implementations, secure auth persistence in storage. Never hand-edit generated files. Comments explain why; avoid implementation-history/requirement-ID noise in production.
10. **Test behavior.** Preserve auth restoration/admission, stale events, callbacks/recovery, sign-out, A → sign-out → B, routing, cleanup, navigation and retained feedback/connectivity behavior. Run focused tests during work and full regressions for substantial shared changes. Finalize with analyzer/tests, implementation guides and project-state updates. Remove dependencies/strings only when proven unused; no opportunistic feature work.

## Feature Code Rules

Approved feature-code amendment, implemented 2026-10-04:

- Screens compose page structure, meaningful sections and navigation callbacks. Dispatch raw input; keep normalization, validation, loading, commands and result decisions out of screen submission methods.
- Cubits own the presentation command flow: normalize → validate → loading → application command → typed feedback/completion. Application owners independently enforce admission and business invariants. Keep controllers, focus and password visibility local to forms; forms collect raw values and invoke callbacks.
- One feature validator owns presentation input rules. When the application independently enforces the same syntax constraint, share its pure rule rather than duplicating the predicate; error mapping remains with each owner. Typed email/password/confirmation errors are separate from backend, storage, network and lifecycle failures; avoid generic error maps and validation frameworks.
- Put rendering dependencies in state. A read-only application snapshot may be projected into Cubit state and updated only by its authoritative owner. Never emit identical presentation data to force widgets to reread hidden state. Private counters/disposal flags may remain mechanical implementation details.
- Extract meaningful headers, forms, feedback/action sections and shared fields/buttons. Split large shared files by responsibility; do not create one file per spacer. Rebuild dynamic sections, keeping static page scaffolds and introductory copy outside command-state builders.
- Repeated typography and style recipes belong to semantic theme/tokens/shared components. Prefer standard controls and Row/Flexible/Expanded; preserve a custom layout only for a measured design/correctness constraint. Existing auth painters remain isolated approved artwork; prefer assets or simple composition for future static art.
- Each destination owns its scrolling and keyboard inset handling. Shell chrome supplies a bounded destination viewport. Avoid alternative scroll ownership modes and nested scroll workarounds.
- main.dart initializes Flutter, awaits focused bootstrap and runs the app. Bootstrap owns dependency injection and external SDK initialization; the app owns providers, theme, locale and router composition.
- Keep the command path readable: intent → Cubit → application/session → repository → data source → SDK → result. SDK notifications reconcile external changes through the same authority. Use integer generations and explicit captured-account checks for stale work; bounded callback replay must never evict in-flight exchanges. Calling signOut means consent was already obtained; cancellation dispatches no command.
- Data sources own SDK operations and persistence barriers; repository implementations map evidence/failures. Email-only operations must not rewrite sessions. Keep implementation dependencies private, handle missing evidence explicitly, and structure persistence suspension so recovery/foreign identity remains deliberately nonpersistent. Retain manual SDK-format writes only for verified timing behavior and document that reason locally.
- Acceptance is human maintainability: a developer can locate typography, fields, validation, presentation feedback, session admission, SDK calls, mapping, storage, callback validation, startup and scrolling without tracing incidental machinery. Add no generic commands, state machines, event buses or pass-through use cases.
